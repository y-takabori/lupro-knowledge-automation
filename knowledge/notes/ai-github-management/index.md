# タイトル案

## 第一候補

非エンジニアがGmail返信AIを実用化するまで：CodexとGitHubで「使える業務効率化ツール」に近づけた話

## 他候補

* AI返信案がズレる問題をどう直したか：Gmail返信アドオン改善の実践記録
* コードが分からなくても業務ツールは作れるのか：Gmail AI返信アドオンをCodexで育てた話
* 非エンジニアが「自分の仕事をラクにするAIツール」をGitHub管理してみた
* メール返信で消耗しないために、Gmail AI返信アドオンを作った話
* AI返信はボタンだけでは足りなかった：実務で使える半自動化の作り方

# このプロジェクトの背景

## 事実

Gmailで開いたメールに対して、AIが返信下書きを作成するアドオンを開発した。

最初の目的は、メール返信にかかる時間を削減することだった。

ただし、単なる時短だけが目的ではなかった。

メール返信は一見すると単純作業に見えるが、実際には相手の意図を読み取り、こちらの対応方針を決め、失礼のない文章に整える必要がある。短い返信であっても、意外と頭を使う。

その結果、メール返信で思考リソースや体力を消耗してしまい、本来もっと頭を使いたいプロジェクトの企画や事業づくりに集中しづらくなる感覚があった。

そこで、メール返信の文章作成部分をAIに任せられないかと考えた。

また、Gmail返信はAI活用のテーマとして比較的分かりやすく、AIを活用した開発や業務効率化に慣れるための最初の題材としてもちょうどよいと考えた。

## 推測

このプロジェクトは、単なるGmail便利ツールではなく、今後のAI業務効率化開発に慣れるための入口でもあった。

返信文作成という身近で分かりやすい業務を題材にすることで、Google Apps Script、AI API、GitHub、Codexといった開発・運用ツールに触れながら、非エンジニアでもAIを使って業務ツールを作れるかを検証する意味があったと考えられる。

# 最初に悩んでいたこと

## 事実

既存のAI返信案は、意図した内容にならないことが多かった。

最初は、Gmailの右側パネルに「AI返信案を作成」ボタンを用意しただけだった。

しかし、ボタンを押しても、AIがこちらの意図を正しく汲み取れず、期待した返信案にならないことが多かった。

原因は、AIが受信メール本文だけを見て返信意図を推測していたこと。

実際のメール返信では、「今回は簡潔に返したい」「丁寧に断りたい」「確認したことだけ伝えたい」「日程候補を出したい」など、ユーザー側の返信方針が重要になる。

## 推測

ユーザーが感じていた違和感は、「AI返信は便利そうだが、最終的に自分でかなり直すなら、実務効率化として弱い」という点だった可能性が高い。

AIに返信文を作らせること自体はできても、自分の意図とズレるたびに修正が必要になるなら、思ったほど時短にならない。

むしろ、AIの返信案を見て「そうじゃない」と感じること自体がストレスになる可能性もある。

そのため、実用化するには、AIが勝手に推測するのではなく、人間が返信方針を渡せる設計が必要だった。

# 本当に解決したかったこと

## 事実

本当に解決したかったのは、メール返信を完全自動化することではない。

むしろ、返信の判断や最終確認は人間が行いながら、文章作成の負担だけをAIに任せることだった。

メール返信では、以下のような判断が毎回発生する。

* すぐに回答するのか
* 一旦確認すると伝えるのか
* 丁寧に断るのか
* 日程候補を提示するのか
* 相手のフォーマットに沿って回答するのか
* 簡潔に済ませるのか、丁寧に補足するのか

この判断までAIに丸投げすると、意図とズレた返信案になりやすい。

そのため、人間が「今回はこう返したい」という方針を入力し、その方針をもとにAIが返信文を作る形を目指した。

## 推測

このプロジェクトの本質は、「返信業務の全自動化」ではなく、「返信に必要な思考のうち、文章化の部分だけをAIに任せること」だった。

ユーザーが担うべきなのは、返信の方向性を決めること。

AIが担うべきなのは、その方向性に沿って、自然なビジネスメールとして整えること。

この役割分担ができると、AI返信アドオンは実務で使える補助ツールに近づく。

# 開発を始める前に考えていたこと

## 事実

既存のアドオンはGoogle Apps Script上に存在していたが、GitHubには保存されていない可能性が高かった。

また、Codexで作業していたものではなく、過去に作成したApps Scriptコードやセットアップマニュアルが手元にある状態だった。

そのため、新たにGitHubリポジトリを作り、そこにコードを保存して、今後はCodexで改善していく方針になった。

## 推測

開発前に考えていたことは、単発で動くツールを作ることではなく、今後も改善できる形にすることだった。

特に、以下のような課題意識があったと考えられる。

* Apps Script上だけにコードがあると管理しづらい
* 変更履歴が残らない
* Codexに依頼しづらい
* 他の人に展開しづらい
* 導入マニュアルやテンプレートとして商品化しづらい
* 一度作って終わりではなく、実務で使いながら改善できる状態にしたい

# 検討した選択肢と迷い

## 事実

最初は、既存のApps Scriptを直接編集する方向もあり得た。

一方で、GitHubに保存してCodexで作業できる形にする方向も検討した。

最終的には、GitHubにPrivateリポジトリを作成し、Codexにファイル構成の作成や改修を依頼する方向にした。

## 迷い

途中で、GitHub Desktopの使い方、Clone、Local path、PC上のフォルダとGitHub上のリポジトリの違いが分かりづらくなった。

また、手動で作ったPCフォルダとGitHubからCloneしたフォルダの違いも混乱ポイントだった。

GitHubブラウザ画面には「File」や「Clone repository」が見当たらず、GitHub Desktopが必要だと分かった。

GitHub Desktopをインストールした後も、保存先のLocal pathをどこにすればよいか、すでに手動で作成したフォルダをどう扱えばよいかで迷った。

## 推測

この迷いは、非エンジニアがAI開発・GitHub管理を始めるときに多くの人がつまずくポイントであり、記事化・商品化するうえで重要な実体験になる。

特に「コードを書く前の環境構築や管理方法が分からない」という壁は、非エンジニア向け導入マニュアルで丁寧に扱う価値が高い。

# 最終的に選んだ進め方

## 事実

最終的には以下の進め方を選んだ。

1. GitHubにPrivateリポジトリを作成
2. GitHub Desktopをインストール
3. PCの `LUPRO_AIdev` フォルダ配下にリポジトリをClone
4. ただし手作業でファイルを作るのが分かりづらくなったため、Codexに作業を依頼
5. Codexが以下のファイルを作成・変更

   * `README.md`
   * `appsscript.json`
   * `Code.gs`
   * `AGENTS.md`
   * `.gitignore`
   * `docs/setup-manual.md`
6. Codexがmainブランチへコミットし、GitHubへpush
7. Apps Script側で `appsscript.json` と `Code.gs` を貼り替え
8. デプロイまで実施

# その判断理由

## 事実

手作業で進める途中で、GitHub DesktopやClone、Local pathなどの理解が難しくなった。

そのため、途中からCodexに依頼して、リポジトリ構成の作成・コード改修・pushまで任せる判断をした。

## 推測

この判断は、実務でAIツール開発を進めるうえで重要だった。

理由は、非エンジニアがすべての技術操作を理解してから進めようとすると、ツール完成前に止まってしまう可能性が高いから。

一方で、ChatGPTに「何をしたいか」「どういう構成にしたいか」「何を守ってほしいか」を整理してもらい、その依頼文をCodexに渡すことで、実装そのものはAIに進めさせられる。

つまり、非エンジニアが担うべき役割は、コードを書くことではなく、以下を言語化することだった。

* 何を解決したいのか
* どこが使いづらいのか
* 実務でどう使いたいのか
* どの情報はAIに渡してよいのか
* どこまで自動化し、どこから人間が確認するのか
* どの状態になれば実務で使えると言えるのか

# 実用化に向けて工夫したこと

## 事実

AI返信案作成前に、「返信方針・要望（任意）」を入力できる欄を追加した。

最初は、Gmailの右側パネルに「AI返信案を作成」ボタンを置いただけだった。

しかし、ボタンを押すだけでは、AIがこちらの意図を十分に理解できず、期待した返信案にならないことが多かった。

そこで、単にボタンを押すだけの設計から、返信前にこちらの要望を入れられるチャット欄・入力欄を設ける方針に変更した。

入力例として、以下のような内容を想定した。

* 確認した旨だけ簡潔に返信したい
* 丁寧にお断りしたい
* 日程候補を3つ提示したい
* 再送をお願いしたい
* 一旦確認して改めて返信すると伝えたい

また、AIプロンプトには「ユーザーの返信方針・要望」を最優先で反映する指示を追加した。

ただし、受信メール本文にない事実、金額、日程、約束を勝手に作らないようにした。

さらに、受信メール本文内にAIへの指示のような文章が含まれていても、それをAIへの命令として扱わないようにした。

## 推測

この工夫により、AI返信アドオンは「勝手に返信文を作るツール」から、「人間の判断を文面化する補助ツール」に近づいた。

実務で使うには、AIの自律性を上げるよりも、人間が意図をコントロールできる余地を残すことが重要だった。

この判断は、実務で使えるツールに近づけるうえで大きな転換点だった。

# Codexやツールが詰まったところ

## 事実

ユーザー側で詰まったポイントは以下。

* GitHub Desktopが入っていなかった
* GitHubブラウザ画面とGitHub Desktopの違いが分かりづらかった
* Cloneの意味が分かりづらかった
* PCで右クリック作成したフォルダと、GitHubからCloneしたフォルダの違いが分かりづらかった
* Local pathの指定に迷った
* 手動で `appsscript.json` や `Code.gs` を作る作業が分かりづらくなった
* 最終的に「もう分からないのでCodexに依頼できないか」という判断になった
* Apps Scriptをどこから開けばよいかも分かりづらかった

## 推測

Codex自体が詰まったというより、Codexに作業させる前段階である「GitHubにコードを置く」「PCフォルダと接続する」「Apps Scriptへ反映する」部分が、非エンジニアにとって大きなハードルだった。

この体験は、導入マニュアルの商品価値に直結する。

特に、非エンジニア向けの商品にする場合は、コードよりも以下を丁寧に説明する必要がある。

* GitHubとは何か
* GitHub Desktopはなぜ必要か
* Cloneとは何か
* PCフォルダとGitHubの関係
* Codexに何を依頼すればよいか
* Apps Scriptのどこに貼り付ければよいか
* APIキーはどこに保存するか
* 何をGitHubに入れてはいけないか

# そこから得た学び

## 事実

GitHubとPCフォルダの接続が完了した後は、Codexに依頼することで一気にリポジトリ構成の整備とコード改修が進んだ。

また、Apps Script側に `appsscript.json` と `Code.gs` を貼り替え、デプロイまで実施した。

## 学び

非エンジニアがAIで業務効率化ツールを作る場合、重要なのは「全部自分で理解すること」ではなく、「AIに任せるための前提を整えること」。

特に重要だったのは以下。

* GitHubに保存して変更履歴を残す
* Codexが読めるルールを `AGENTS.md` に残す
* APIキーや個人情報をコードに入れない
* READMEやsetup manualを整備して、後から自分や他人が使える形にする
* 実装指示には、機能要件だけでなく、テスト観点・期待挙動・セキュリティ注意点も含める
* 完全自動化を目指すのではなく、人間が判断を残せる半自動化にする
* AIに任せるには、AIに渡す情報の設計が重要になる

# 業務効率化につながりそうな点

## 事実

メール本文をもとにAIが返信下書きを作成できる。

日程調整メールでは、Googleカレンダーの空き候補を反映できる設計になっている。

ユーザーが返信方針を入力できるようになったことで、AI返信案の意図ズレを減らせる可能性がある。

## 推測

業務効率化につながる点は以下。

* メール返信文を考える時間の削減
* メール返信で消耗する思考体力の削減
* 日程候補確認の手間削減
* 返信漏れ・対応遅れの防止
* 文章作成が苦手な人の負担軽減
* 社内メンバーへの展開可能性
* 同じ仕組みを他社向けに導入支援できる可能性
* AI開発・業務効率化に慣れるための入口になる

# X/Threads投稿案

## 投稿案1

メール返信って、地味だけど意外と頭を使う。

相手の意図を読んで、こちらの対応方針を決めて、失礼のない文章にする。
短い返信でも、少しずつ思考体力を削られる。

だからGmail返信AIを作った。

でも最初はボタンを押すだけだったので、意図した返信にならなかった。
大事だったのは「今回はこう返したい」を入力できる設計でした。

## 投稿案2

GmailのAI返信アドオンを作ってみて分かったこと。

「AI返信案を作成」ボタンだけでは足りない。

実務では、
・簡潔に返したい
・丁寧に断りたい
・確認した旨だけ伝えたい
・日程候補を出したい
みたいな返信方針がある。

AIに必要だったのは、性能より先に「意図を渡す入力欄」だった。

## 投稿案3

AI業務効率化で大事なのは、全部AIに任せることではない。

今回のGmail返信AIも、返信方針は人間が決める。
AIはその方針に沿って文面化する。
最後の送信判断も人間がする。

全自動より、実務ではこの半自動の方が安心して使える。

## 投稿案4

非エンジニアがAIツール開発で詰まるのは、コードよりも意外とGitHub周り。

リポジトリ、Clone、Local path、GitHub Desktop。
このあたりで普通に迷う。

でも一度GitHubに置けると、Codexに改善を依頼できるようになる。
ここがかなり大きな分岐点でした。

## 投稿案5

Gmail返信AIを作った理由は、返信時間を減らしたかったから。

でも本音を言うと、メール返信で頭を使いすぎたくなかった。

返信文に消耗するより、プロジェクトの企画や事業づくりに頭を使いたい。

AI業務効率化って、単なる時短ではなく「思考体力の使いどころを変える」ことでもある。
